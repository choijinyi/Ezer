|---|---|---|---|

## 학습 목표

이 회차를 마치면 다음을 할 수 있다.

- CBS M&C의 실제 업무 병목 하나를 골라, 풀 수 있는 크기의 **과제로 정의**하고 성공 지표를 숫자로 세울 수 있다.
- 1~5회차에서 익힌 기술 모듈(STT·영상 분석·검색·생성)을 **하나의 파이프라인으로 조립**할 수 있다.
- 앞 회차 코드를 함수로 불러와, 한 개 실제 케이스를 **end-to-end로 돌리는 통합 스크립트**를 작성할 수 있다.
- 자동화 전후 소요 시간과 정확도를 **측정**해 개선 효과를 정량으로 제시할 수 있다.
- 결과를 루브릭에 맞춰 **발표**하고, PoC 피드백 루프로 이어 갈 수 있다.

## 1. PBL이란 무엇인가

**[개념]** PBL(Problem-Based Learning, 문제기반학습)은 *강의를 듣고 끝나는* 방식이 아니라, **실제 문제를 받아 직접 풀어 가며 배우는** 방식이다. 정답이 미리 정해져 있지 않고, 학습자가 문제를 정의하고·자료를 모으고·해법을 만들고·검증하는 과정 자체가 학습이다.

이 회차의 목적은 분명하다. 1~5회차는 기술을 *따로따로* 배우는 모듈이었다. LLM·프롬프트(1회), STT(2회), 영상·멀티모달(3회), 임베딩·검색·중복(4회), 생성·숏폼·TTS·자막(5회) — 각각은 도구 한 개다. 그러나 CBS의 실제 병목은 도구 한 개로 풀리지 않는다. **여러 모듈을 순서대로 이어 붙인 파이프라인**이라야 "콘텐츠 1건당 3~6시간, 그중 소재 탐색이 30~50%"라는 실제 병목에 손을 댈 수 있다.

그래서 6회차는 강의가 아니라 **프로젝트 진행 가이드**다. 정해진 결론을 따라오는 것이 아니라, 각자(또는 팀이) 고른 과제를 직접 굴려 본다.

**진행 흐름**은 다음 네 단계다.

```
[1] 과제 선정·범위 정의   →  무엇을, 어디까지, 어떤 지표로 풀 것인가
        │
[2] 파이프라인 설계        →  1~5회차 모듈 중 어떤 것을 어떤 순서로 이을까
        │
[3] 프로토타입 구현(PoC)   →  실제 케이스 1건을 end-to-end로 돌린다
        │
[4] 효과 측정·발표         →  전후 비교·검수 결과를 루브릭에 맞춰 제시
```

**[팁]** 이 흐름은 그대로 7회차 CBL과 PoC 피드백 루프(3회전)로 이어진다. 6회차는 "한 케이스가 정말 돌아가는가"를 증명하는 1회전이고, 7회차에서 이를 전사 효율화·운용 가이드로 확장한다. 그러니 6회차의 산출물(과제 정의서·코드·측정표)은 **버리지 말 것.**

## 2. 과제 선정과 범위 정의

### 2.1 CBS 실제 병목 후보

**[개념]** 좋은 PBL 과제는 "멋진 기술"이 아니라 **"아픈 병목"**에서 나온다. 사업계획서가 짚은 CBS의 실제 병목 — 콘텐츠 1건당 3~6시간, 소재 탐색이 30~50% — 을 기준으로 후보를 좁힌다. 아래 표에서 **하나만** 고른다(욕심내지 않는다).

| 후보 과제 | 푸는 병목 | 주로 쓰는 회차 모듈 | 한 케이스 입력 예시 |
|---|---|---|---|
| 소재 탐색 자동화 | 소재 탐색 30~50% | 2(STT)·4(검색·중복)·1(추출) | 노컷TV 영상/녹취에서 기사화 후보 뽑기 |
| 기사 초안 생성 | 기사 작성 시간 | 2(STT)·1(LLM 초안)·4(중복 점검) | 인터뷰 녹취 → 방송 리드·기사 초안 |
| 아카이브 영상 검색·태깅 | 자료 탐색·재활용 | 2(STT)·3(영상 태깅)·4(벡터 검색) | 뉴스 영상 아카이브에 의미 검색 붙이기 |
| 숏폼 자동화 | 편집·재가공 공수 | 2·3·4·1·5 전부 | 긴 영상 → 하이라이트 → 숏폼 대본·자막 |

**[팁]** 처음이라면 **모듈 2~3개로 끝나는 과제**(소재 탐색, 기사 초안)부터 권한다. 5개 모듈을 다 엮는 숏폼 자동화는 가장 화려하지만 디버깅 면적도 가장 넓다. "10시간 안에 한 케이스가 끝까지 도는가"가 선정의 1순위 기준이다.

### 2.2 범위와 성공 지표 정의

**[개념]** 과제를 골랐으면 **범위(scope)**를 못 박는다. PBL이 실패하는 가장 흔한 이유는 기술 부족이 아니라 **범위 과욕**이다. "아카이브 전체를 검색"이 아니라 "**영상 20건**에 의미 검색을 붙인다"처럼 끝을 숫자로 막는다.

성공 지표도 숫자여야 한다. 막연한 "편해졌다"가 아니라 **베이스라인(자동화 전 수동 소요) 대비 절감률**과 **정확도 표본 검수 결과**로 잡는다.

- 시간 지표: 기존 수동 1건 30분 → 자동화 후 8분 = **약 73% 절감** (목표를 미리 정한다, 예: 50% 이상)
- 품질 지표: 자동 생성 결과 표본 10건 중 사람 검수 통과 N건 = **정확도/유용도**

### 2.3 과제 정의서 템플릿

아래 표를 채우는 것이 [실습 1]이다. 빈칸은 실습에서 채운다.

| 항목 | 내용 |
|---|---|
| 과제명 | (예) 노컷TV 영상에서 기사 소재 후보 자동 추출 |
| 푸는 병목 | (예) 소재 탐색에 건당 1~2시간 소요 |
| 입력 데이터 | (예) 노컷TV 인터뷰 영상 1건(약 20분) |
| 사용 모듈(회차) | (예) 2회 STT → 1회 소재 추출 → 4회 기존 기사 중복 점검 |
| 산출물 | (예) 기사화 후보 5개 + 각 근거 타임코드 + 중복 경고 |
| 성공 지표(시간) | (예) 수동 60분 → 자동 15분, 목표 절감 50%↑ |
| 성공 지표(품질) | (예) 후보 5개 중 데스크 채택 3개 이상 |
| 범위 밖(하지 않을 것) | (예) 영상 여러 건 일괄 처리, 발행 자동화 |
| 사람 검수 게이트 | (예) 후보 채택·기사화 결정은 기자/데스크가 한다 |

**[주의]** "**범위 밖**" 칸과 "**사람 검수 게이트**" 칸을 비워 두지 말 것. 무엇을 *안 할지*를 정해야 10시간 안에 끝나고, 검수 게이트를 명시해야 자동화가 사람의 판단을 대체하는 사고를 막는다.

## 3. 파이프라인 설계: 1~5회차 모듈 조립

**[개념]** 파이프라인은 **"앞 단계의 출력이 다음 단계의 입력"**이 되도록 모듈을 줄 세운 것이다(1회차 2.4 프롬프트 체이닝의 확장판). 각 모듈은 *함수* 하나라고 생각하면 된다 — 입력을 받아 가공해 다음으로 넘긴다.

아래는 가장 종합적인 예시인 **아카이브 영상 → 숏폼**의 조립도다. 자신이 고른 과제에서는 필요한 칸만 남기고 잘라 쓴다.

```
[입력] 아카이브 영상 1건 (.mp4)
   │
   ▼
(2회) STT(WhisperX)        영상의 말 → 타임코드 붙은 텍스트
   │  출력: segments[{start, end, text}]
   ▼
(3회) 영상 태깅(Gemini)     장면·인물·키워드 → 구조화 JSON
   │  출력: {scenes, keywords, ...}
   ▼
(4회) 검색·중복 점검         임베딩 → 기존 기사 DB와 유사도 비교
   │  출력: 중복 경고 / 신선도 점수
   ▼
(1회) 소재 추출(LLM)         자막+태그 → 기사화 후보·하이라이트 구간
   │  출력: [{소재, 근거 타임코드, 리드 초안}]
   ▼
(5회) 숏폼 대본·자막·TTS      후보 1개 → 숏폼 대본 + 자막(.srt) + 내레이션
   │
   ▼
[산출물] 숏폼 대본 + 자막 + (선택) 내레이션 음성
                                  └─▶ [사람 검수 게이트] 발행 결정은 사람
```

설계할 때 정할 것은 세 가지다.

- **데이터 형식(인터페이스)** — 모듈 사이를 흐르는 데이터의 모양을 미리 정한다. 예: STT는 `[{"start": 0.0, "end": 4.2, "text": "..."}]` 리스트를 내보내고, 소재 추출은 그 리스트를 받는다. 형식을 못 박으면 모듈을 갈아 끼우기 쉽다.
- **저장 지점** — 단계마다 중간 결과를 파일로 떨군다(`01_stt.json`, `02_tags.json` …). 한 단계가 실패해도 처음부터 다시 돌릴 필요가 없고, 재현·디버깅이 쉽다.
- **검수 게이트 위치** — 자동으로 흘리되, **사람이 반드시 확인할 지점**을 표시한다. 위 예시에서는 마지막 발행 결정이지만, 소재 추출 직후에 한 번 더 두어도 좋다.

**[주의]** 모듈을 이을 때 **프롬프트·모델·파라미터를 코드 안에 기록**하라(1회차 temperature 설정처럼). "그때는 됐는데 지금은 안 된다"의 90%는 어떤 프롬프트·모델을 썼는지 기록하지 않아서 생긴다. 재현성은 PoC의 생명이다.

## 4. 실습(프로젝트 진행)

> 공통 준비: 파이썬 3.10+, 1~5회차에서 만든 코드(또는 강사가 배포한 모듈), 환경 변수 `GEMINI_API_KEY`. 외부 API가 제한되면 강사가 안내하는 사내 게이트웨이를 쓴다. 샘플 입력 1건(영상 또는 녹취)을 미리 준비한다.

### [실습 1] 과제 정의서 작성 (60분)

2.3의 템플릿 표를 **자신의 과제로 채운다.** 팀이면 화면에 띄워 함께 합의한다. 채울 때 다음을 자가 점검한다.

- 성공 지표가 **숫자**인가? ("편해진다"는 지표가 아니다.)
- "범위 밖" 칸에 **하지 않을 것**이 적혀 있는가?
- "사람 검수 게이트"가 명시되어 있는가?
- 입력 데이터 **1건**을 실제로 준비할 수 있는가? (없으면 과제를 바꾼다.)

작성한 정의서는 [실습 3] 측정과 7회차 CBL의 출발 자료다.

### [실습 2] 파이프라인 프로토타입 구현 (150분)

앞 회차에서 만든 코드를 **함수로 불러와** 한 케이스를 end-to-end로 돌린다. 핵심은 *새 기술을 배우는 것이 아니라, 이미 가진 모듈을 함수로 호출해 잇는 것*이다. 아래는 "소재 탐색 자동화" 과제의 통합 스크립트 예시다 — 단계마다 `print`로 진행을 보이고, 중간 결과를 파일로 저장한다.

```python
"""
PBL 통합 파이프라인 (예: 소재 탐색 자동화)
영상 1건 → STT(2회) → 소재 추출(1회) → 기존 기사 중복 점검(4회)
각 단계 결과를 out/ 에 저장하고, 마지막에 사람 검수용으로 출력한다.
"""
import os, json, time, pathlib
from google import genai
from google.genai import types

# 앞 회차에서 만든 모듈을 함수로 가져온다(파일명은 각자 환경에 맞게).
from stt_module import transcribe          # 2회차: 영상→타임코드 자막
from search_module import find_duplicates  # 4회차: 임베딩 기반 기존 기사 유사도

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
OUT = pathlib.Path("out"); OUT.mkdir(exist_ok=True)

def save(name, obj):
    """중간 결과를 파일로 떨궈 재현·디버깅을 쉽게 한다."""
    (OUT / name).write_text(json.dumps(obj, ensure_ascii=False, indent=2), encoding="utf-8")
    print(f"  └─ 저장: out/{name}")

# ── 1단계 (2회) STT ──────────────────────────────
print("[1/3] STT: 영상→자막")
t0 = time.time()
segments = transcribe("input/interview.mp4")   # [{start,end,text}, ...]
save("01_stt.json", segments)
transcript = " ".join(s["text"] for s in segments)

# ── 2단계 (1회) 소재 추출: 구조화 출력 ───────────────
print("[2/3] 소재 추출: 자막→기사화 후보(JSON)")
schema = {
    "type": "object",
    "properties": {
        "candidates": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "topic":    {"type": "string"},
                    "lead":     {"type": "string", "description": "방송 리드 2문장 이내"},
                    "evidence": {"type": "string", "description": "근거가 된 발언 일부"},
                },
                "required": ["topic", "lead", "evidence"],
            },
        }
    },
    "required": ["candidates"],
}
resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=f"다음 인터뷰 녹취에서 기사화할 만한 소재 후보 5개를 뽑아라. 과장 없이 사실 기반으로.\n\n{transcript}",
    config=types.GenerateContentConfig(
        temperature=0.2,            # 사실 작업: 낮게(1회차)
        response_mime_type="application/json",
        response_schema=schema,
    ),
)
candidates = json.loads(resp.text)["candidates"]
save("02_candidates.json", candidates)

# ── 3단계 (4회) 중복 점검 ─────────────────────────
print("[3/3] 중복 점검: 기존 기사 DB와 유사도 비교")
for c in candidates:
    dup = find_duplicates(c["topic"] + " " + c["lead"])   # [{title, score}, ...]
    c["dup_warning"] = dup[0] if dup and dup[0]["score"] > 0.85 else None
save("03_candidates_checked.json", candidates)
elapsed = round(time.time() - t0, 1)

# ── 산출물: 사람 검수용 출력 ───────────────────────
print(f"\n=== 완료 (소요 {elapsed}s) — 채택은 사람이 결정 ===")
for i, c in enumerate(candidates, 1):
    flag = "  [중복 경고]" if c["dup_warning"] else ""
    print(f"{i}. {c['topic']}{flag}\n   리드: {c['lead']}\n   근거: {c['evidence'][:60]}...")
```

**[팁]** 앞 회차 코드가 함수로 깔끔히 분리돼 있지 않다면, 먼저 `def transcribe(path): ...`처럼 **입력→출력이 분명한 함수로 감싸는 것**부터 한다. 파이프라인 구현의 절반은 "이미 만든 코드를 함수로 정리"하는 일이다.

**[주의]** 통합 스크립트는 한 번에 다 완성하려 하지 말고 **단계별로 돌려 확인**한다. 1단계 STT만 돌려 `01_stt.json`을 눈으로 보고, 멀쩡하면 2단계를 붙인다. 중간 저장 파일이 그대로 디버깅 로그가 된다. 또한 사내 영상·녹취·취재원 정보를 외부 API에 보내기 전, 처리 범위와 민감 정보 포함 여부를 먼저 확인한다(개인정보·보안).

### [실습 3] 효과 측정과 발표 준비 (90분)

프로토타입이 돌면, 과제 정의서의 지표대로 **전후를 비교**한다. 인상이 아니라 숫자로.

**개선 효과 측정표** — 같은 케이스 1건을 (가능하면) 수동으로도 해 보고 시간을 잰다.

| 항목 | 기존(수동) | 자동화 후 | 절감/개선 |
|---|---|---|---|
| 소요 시간(1건) | 예) 60분 | 예) 15분(스크립트 12분+검수 3분) | 약 75% |
| 사람이 하는 일 | 영상 보며 메모·검색 | 후보 채택·검수만 | 판단에 집중 |
| 산출물 수 | 후보 2~3개 | 후보 5개 | — |

**정확도 표본 검수표** — 자동 결과의 품질을 표본으로 확인한다(자동화해도 검수는 사람의 몫).

| 표본 | 자동 생성 결과 | 사실 정확 | 유용(채택 가능) | 비고 |
|---|---|---|---|---|
| 후보 1 | (소재명) | O/X | O/X | |
| 후보 2 | | O/X | O/X | |
| … | | | | |
| **합계** | | OO% | OO% | 목표 대비 |

**발표 준비(5분 분량)** — 다음 순서로 슬라이드 또는 한 페이지를 만든다.

1. **문제** — 어떤 병목을, 왜 골랐나(시간 숫자로).
2. **설계** — 어떤 회차 모듈을 어떤 순서로 이었나(3장 조립도 한 장).
3. **데모** — 한 케이스의 입력→산출물(실제 출력 화면).
4. **효과** — 측정표 두 개(시간·정확도).
5. **한계와 다음 단계** — 검수 게이트, 범위 밖, 7회차로 확장할 점.

**[주의]** 발표에서 **숫자와 한계를 함께** 말한다. "75% 절감"만 말하고 "표본 10건 중 사실 오류 1건이 있어 검수가 필수"를 빼면 PoC가 아니라 광고가 된다. PoC 피드백 루프는 한계를 드러내야 다음 회전이 돌아간다.

## 7. 핵심 요약

- PBL은 강의가 아니라 **실제 병목을 직접 풀며 배우는** 프로젝트다. 6회차의 목적은 1~5회차 모듈을 조립해 **CBS 병목 한 케이스를 end-to-end로 증명**하는 것이다.
- 좋은 과제는 화려함이 아니라 **풀 수 있는 크기**에서 나온다. 범위를 못 박고, 성공 지표를 **숫자**로 세운다.
- 파이프라인은 **앞 단계 출력 = 다음 단계 입력**으로 모듈을 줄 세운 것이다. 데이터 형식·중간 저장·검수 게이트를 미리 정한다.
- 구현의 절반은 **앞 회차 코드를 함수로 정리해 import·호출**하는 일이다. 단계별로 돌려 가며 붙인다.
- 효과는 **전후 시간 절감률과 표본 검수**로 제시하고, **한계를 함께** 말한다. 코드·프롬프트·파라미터 기록(재현성)과 사람 검수 게이트는 필수다.

## 8. 다음 회차 예고

**7회차 · CBL 도전 과제 — AI 업무 효율화 설계(10H)** — 6회차에서 한 케이스로 증명한 프로토타입을, 이제 **개인의 실험에서 전사의 시스템으로** 끌어올린다. 한 건이 아니라 매일 들어오는 콘텐츠에 안정적으로 적용하려면 무엇이 필요한가 — 운용 가이드(누가·언제·어떻게 돌리고 검수하는가), 실패·예외 처리, PoC 피드백 루프 3회전, 그리고 AX 실행계획으로의 연결. 6회차 산출물(과제 정의서·코드·측정표)이 그대로 7회차의 출발점이 되므로, **반드시 보관**해 두자.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| PBL(문제기반학습) | 실제 문제를 직접 정의·해결하며 배우는 학습 방식. 정답이 미리 주어지지 않는다 |
| CBL(도전기반학습) | PBL을 확장해 더 큰 도전 과제를 전사 관점에서 설계·실행하는 학습 방식 |
| PoC | Proof of Concept. 아이디어가 실제로 작동함을 작은 범위로 증명하는 시제품 |
| 피드백 루프 | PoC를 돌려 결과·한계를 보고 개선해 다시 돌리는 반복 회전(이 과정은 3회전 설계) |
| 파이프라인 | 앞 단계의 출력이 다음 단계의 입력이 되도록 모듈을 줄 세운 처리 흐름 |
| 모듈 | 입력→출력이 분명한 독립 단위(여기서는 각 회차의 기술 함수) |
| 인터페이스 | 모듈 사이를 흐르는 데이터의 약속된 형식(모양) |
| 베이스라인 | 자동화 전 수동 방식의 기준 성능(소요 시간 등). 개선 효과 측정의 비교 대상 |
| 범위(scope) | 이번에 풀 것과 풀지 않을 것의 경계. 못 박지 않으면 과욕으로 실패한다 |
| 검수 게이트 | 자동 흐름 중간·끝에서 사람이 반드시 확인·결정하는 지점 |
| 재현성 | 코드·프롬프트·파라미터를 기록해 누구나 같은 결과를 다시 얻을 수 있는 성질 |
